# Backend Sync Design Spec

**Date:** 2026-08-12
**Status:** Approved
**Scope:** Wire the scaffolded Express + tRPC + Drizzle backend to the app for cloud sync of all user data (watchlist, price alerts, settings, back-order reminders + stock watches) on both mobile (iOS/Android/web) and the Tauri desktop app, using optional Manus OAuth login. Server-side scraping is explicitly **out of scope** this phase — this phase is "sync now, scrape later."

## Overview

Today the app is local-only via AsyncStorage (`lib/storage.ts`), while `server/` (Express + tRPC v11 + Drizzle/MySQL + Manus OAuth) is fully scaffolded but unused — only a `users` table and `system`/`auth` routers exist. This feature connects the two: a user signs in with Manus OAuth (optional), and their watchlist, alerts, settings, and reminders sync to the cloud and back across devices.

Key design decisions (confirmed with the user):

1. **Sync now, scrape later** — no server-side scraping; sync architecture leaves room for it later.
2. **Optional login** — app stays fully local-first when signed out; no sync errors surfaced to logged-out users.
3. **Timestamp-based per-item sync**, last-write-wins per item.
4. **Automatic sync** on launch + on mutations (debounced), with a subtle status indicator in Settings.
5. **All user data syncs**: watchlist, price alerts, app settings, back-order reminders + stock watches.
6. **Latest-state-only** — only the latest listing state (price/stock/currency/lastChecked) syncs; the 90-day `priceHistory` stays local per device.
7. **Fully normalized Drizzle tables**, server-side per-item merge.
8. **Mobile + desktop both** sync this phase (desktop gets auth + network layer from scratch).
9. Desktop OAuth via **localhost loopback callback** (Tauri Rust listener on port 3420).
10. Desktop tRPC via **React Query** (adds `@tanstack/react-query` + `@trpc/react-query` to desktop).

## Server: Drizzle schema (new tables)

Add to `drizzle/schema.ts` (replace the `// TODO: Add your tables here` comment). One row per item, composite PK of `(userId, itemId)`, JSON payload column, plus sync metadata. Following the existing `users` table conventions (camelCase columns).

| Table | PK | Payload column | Notes |
|---|---|---|---|
| `watchlist_items` | `(userId, productId)` | `data` (JSON: Product minus `priceHistory`) | latest state only |
| `price_alerts` | `(userId, alertId)` | `data` (JSON: PriceAlert) | |
| `back_order_reminders` | `(userId, reminderId)` | `data` (JSON: BackOrderReminder) | covers date reminders + stock watches |
| `app_settings` | `(userId)` | `data` (JSON: AppSettings) | single row per user |

Every row also has:
- `updatedAtMs: bigint` — epoch ms set on every upsert (last-write-wins key). Epoch-ms `bigint` (not a `timestamp` column) so client `Date.now()` values compare exactly and we avoid second-precision collisions.
- `deletedAtMs: bigint` (nullable) — tombstone (epoch ms); when set, row is considered deleted.

`userId` references `users.id` (the surrogate int PK).

Types generated by `$inferSelect` / `$inferInsert` as in `users`.

## Server: tRPC sync router

Add a `sync` router to `server/routers.ts` (replacing the `// TODO: add feature routers here` comment), both procedures under `protectedProcedure` (so `ctx.user` is non-null).

### `sync.pull`

```
query sync.pull({ since: number | null }) -> {
  lastSyncedAt: number;
  items: SyncItem[];
}
```

- `since` is the client's `lastSyncedAt` epoch ms (from its `sync_meta`), or `null` for first sync.
- Returns all rows for the user where `updatedAtMs > since` OR `deletedAtMs > since`, across all four collections, plus the server's current `Date.now()` as `lastSyncedAt` so the client can advance its cursor.
- Each `SyncItem = { collection: "watchlist" | "alerts" | "reminders" | "settings"; id: string; data: unknown; updatedAt: number; deletedAt: number | null }` (epoch ms). `data` is `null` when `deletedAt` is set (client only needs the tombstone).
- Empty result set when nothing changed.

### `sync.push`

```
mutation sync.push({ items: SyncItem[] }) -> { accepted: number }
```

- Server-side last-write-wins: for each item, upsert only if `incoming.updatedAt > existing.updatedAt` (or row doesn't exist). If incoming `deletedAt` is set, either soft-delete (set `deletedAt`) or hard-delete the row — prefer **soft-delete then let pull tombstones propagate**, and the server can hard-purge rows with `deletedAt` older than e.g. 30 days.
- Returns count of accepted items (useful for logging/debug).

### DB availability

All sync handlers call `getDb()` (from `server/db.ts`) and return an empty/no-op result if it returns `null` (no `DATABASE_URL` configured) — the server stays up in local-only deployments. Log a warning.

## Client: shared sync engine — `lib/sync.ts` (new)

Works identically on mobile and desktop (desktop imports it via relative path `../../lib/sync`, same pattern as `lib/price-digest`).

### Sync metadata — `lib/storage.ts`

New AsyncStorage key `sync_meta`:

```
type SyncMeta = {
  lastSyncedAt: number;                       // epoch ms
  items: Record<string, Record<string, {     // [collection][itemId]
    updatedAt: number;
    deleted: boolean;
  }>>;
};
```

Add `getSyncMeta()`, `saveSyncMeta()`, plus `setItemSyncMeta(collection, id, updatedAt)`, `clearItemSyncMeta(collection, id)` helpers. Add `sync_meta` to `clearAllData` legacy-key cleanup. Domain types (`Product`, `PriceAlert`, etc.) are **not** modified — sync metadata lives entirely in this separate store.

### Sync engine API

```
type Collection = "watchlist" | "alerts" | "reminders" | "settings";

syncNow(opts: {
  storage: Storage;                 // createStorage instance
  isSignedIn: () => boolean;        // resolves current auth state
  pull: (since: number | null) => Promise<{ lastSyncedAt: number; items: SyncItem[] }>;
  push: (items: SyncItem[]) => Promise<{ accepted: number }>;
  now?: () => number;               // injectable clock for tests
}): Promise<void>
```

Steps:

1. If `!isSignedIn()` → return (no-op).
2. **Pull**: call `pull(syncMeta.lastSyncedAt ?? null)`.
3. **Merge pulled items into local storage** (server wins per-item by `updatedAt`):
   - watchlist item → read `getWatchlist()`, upsert the product if `pulled.updatedAt > local meta.updatedAt`, preserving **local `priceHistory`** for each listing (history stays local). If tombstone (`deletedAt` set) and `pulled.updatedAt > local meta` → `removeFromWatchlist`.
   - alerts → same pattern against `getAlerts()` / `saveAlerts` / remove.
   - reminders → merge both `back_order_reminders` and `back_in_stock_watches` arrays (they share `BackOrderReminder` shape, discriminated by `reminderType`).
   - settings → single object; merge if server `updatedAt` newer.
   - Advance local meta `updatedAt`/`deleted` for each applied item.
4. **Push local changes**: collect items whose meta `updatedAt > lastSyncedAt` (dirty), serialize current local state into `SyncItem`s (strip `priceHistory` for watchlist), call `push`. On success, set `lastSyncedAt = max(pulled.lastSyncedAt, now())`.
5. Wrap in a single in-flight lock (module-level promise) so concurrent calls don't interleave; re-enter is a no-op while running.

### Mutation tracking

`lib/storage.ts`'s mutating functions (`addToWatchlist`, `removeFromWatchlist`, `updateProductListings`, alert save/remove, reminder save/remove, `saveSettings`) get a companion `markDirty(collection, id)` call so the engine knows what changed. To keep `createStorage` generic and testable, add an optional `onChange?: (key, itemId) => void` callback param to `createStorage(adapter, opts)` that fires after each successful mutation; the sync engine subscribes through it.

### Merge rule summary

- Per-item last-write-wins by `updatedAt` (client clock vs server clock; client sets `updatedAt` from `Date.now()` on mutation; server trusts incoming but only accepts newer-than-existing).
- Server tombstone → local removal.
- Pulled listing state replaces local listing state **per listing** (`price`, `stockStatus`, `currency`, `url`, `lastChecked`), but `priceHistory` array preserved.
- Settings single-object last-write-wins.

## Auth

### Mobile (existing flow, reused)

- `lib/_core/auth.ts` (SecureStore token native / cookie web), `hooks/use-auth.ts`, `app/oauth/callback.tsx`, `constants/oauth.ts` (`startOAuthLogin`, `getLoginUrl`) all already exist.
- Add a **Sign in** button in Settings that calls `startOAuthLogin()`; on native it opens the system browser → deep link back to `/oauth/callback`. On web it redirects → server sets cookie → callback route.
- After sign-in completes, trigger a first `syncNow()` (pull existing cloud data and merge).
- Add **Sign out** (calls `Api.logout()`, clears token/user info) — local data remains, no deletion prompt needed this phase.

### Desktop (new: localhost loopback)

Desktop has no deep links. Flow:

1. Settings "Sign in" → call a new Tauri command (e.g. `start_oauth`) that:
   - Starts a tiny HTTP listener on `127.0.0.1:3420`.
   - Opens the system browser to `${OAUTH_PORTAL_URL}/app-auth?...&redirectUri=http://localhost:3420/callback`.
2. The portal redirects the browser to `http://localhost:3420/callback?sessionToken=...&user=...`.
3. The Rust listener captures the query params, stores `sessionToken` via the existing frontend auth layer (SecureStore-equivalent: desktop uses `localStorage`), and returns a success to the frontend promise.
4. Desktop then calls `syncNow()`.

Implementation notes:
- Tauri command in `desktop/src-tauri/src/lib.rs`: spawn a `TcpListener` on `127.0.0.1:3420`, accept one connection, read the HTTP request line, extract query params, respond with a minimal HTML/JS "You can close this window", resolve the command with the token.
- Frontend `desktop/src/hooks/use-auth.ts` (new): wraps `getSessionToken`/`setSessionToken`/`getUserInfo`/`setUserInfo` (mirrors `lib/_core/auth.ts` but `localStorage`-based; note `getSessionToken` returns `null` on web platform in the shared module — desktop must use its own store, so do **not** reuse `lib/_core/auth.ts` for desktop).
- `getApiBaseUrl()` from `constants/oauth.ts` is not directly reusable on desktop (imports `expo-linking`/`react-native`). Add a small desktop equivalent (`desktop/src/lib/api-base.ts`) that reads `VITE_API_BASE_URL` and falls back to the same `http://localhost:3000`.

## Data Flow

1. **Launch (signed in):** `app/_layout.tsx` (mobile) / `desktop/src/App.tsx` (desktop) → after auth resolves → `syncNow()` → pull → merge → push dirty.
2. **Mutation:** any storage write fires `onChange` → debounced (~2s) `syncNow()`.
3. **Price check:** after `checkPriceDropsNow`/`updateProductListings` complete, the same debounced sync picks up the new listing state.
4. **Sign in:** first `syncNow()` after auth → pulls existing cloud data onto the device.
5. **Multi-device:** each device runs the same pull/merge/push; last-write-wins reconciles conflicts.

## Error Handling

- **Not signed in** → `syncNow` no-op.
- **Network failure / server down** → catch, mark offline, do not crash; local-first continues; next successful sync reconciles.
- **No `DATABASE_URL` on server** → sync returns empty results; clients see no data and no error.
- **`getDb()` null** → handlers return empty, log warning.
- **Superjson serialization** of domain objects (Date/undefined) — already the project transformer; `SyncItem.data` must be superjson-serializable (plain JSON objects — keep `lastRefreshed`/`createdAt` as ISO strings as they already are). Sync timestamps (`updatedAt`/`deletedAt`/`lastSyncedAt`) are plain epoch-ms numbers end to end.

- Realtime push / WebSockets (poll/pull on launch + mutation only)
- Desktop OAuth refresh handling (token expiry → re-sign-in; note as follow-up)
